# Что меняется при переносе списка внутрь gather

В обеих версиях запросы выполняются конкурентно. Вынос списка в переменную
не даёт отдельного асинхронного ускорения. Разница в основном касается
читаемости и времени жизни контейнера списка.

## Что делает Python

```python
tasks = [fetch(client, url) for url in URLS]
await asyncio.gather(*tasks)
```

Здесь `fetch` — функция, объявленная через `async def`. Поэтому её вызов создаёт
объект корутины: тело `fetch` ещё не исполняется. Сначала создаётся весь список.
Имя `tasks` немного сбивает с толку: на этом этапе это список корутин.
Его можно назвать `coroutines`.

Затем `*tasks` распаковывает элементы в позиционные аргументы `gather`.
`gather` оборачивает переданные корутины в задачи и планирует их выполнение.
`await` ждёт итоговый результат. Пока запрос ждёт сеть, event loop может
исполнять другие запланированные задачи.

```python
await asyncio.gather(*[fetch(client, url) for url in URLS])
```

Во второй записи порядок этих действий такой же: построить весь список,
распаковать его, вызвать `gather`, дождаться результата. Запросы не начинают
выполняться по одному во время построения этого списка.

## Что заметно на большом числе URL

В CPython список, записанный в локальную переменную `tasks`, остаётся доступен
в кадре функции во время `await`. Во второй записи временный контейнер списка
уже не нужен после подготовки аргументов вызова и может освободиться раньше.
Это контейнер ссылок на корутины: его освобождение не означает освобождения
самих корутин, пока задачи их используют.

На 64-битной машине одна ссылка обычно занимает 8 байт; кроме ссылок, у списка
есть заголовок и запас ёмкости. Для миллиона элементов это примерно 8 МиБ
порядка величины, а точный размер зависит от реализации и выделенной ёмкости.
Память самих корутин, задач, ожиданий и результатов может быть гораздо больше.

Поэтому разница в удерживаемой памяти реальна, но обе версии по-прежнему
создают O(N) корутин и задач. Нельзя обещать заметное ускорение загрузки
только от переноса списка в строку вызова. Сравнение по публичной сети
дополнительно зависит от сервера, соединений и кешей.

`gather_nuance.py` проверяет это на 100, 10 000 и 50 000 элементах.
Вместо HTTP используются корутины, ожидающие один `Event`. Пока они ждут,
измеряются число живых задач, размер локального списка и память Python.
Время измеряется с включённым `tracemalloc`, поэтому оно не является
чистым тестом производительности и тем более скоростью скачивания.

В запуске 31.10.2026 на CPython 3.12.14 при 50 000 элементах локальный
список занимал 444 376 байт. Память Python во время ожидания составила
55.22 МиБ со списком в переменной и 54.79 МиБ со списком внутри вызова.
В обоих случаях было 50 000 дочерних задач. Медианное время трёх повторов
округлилось до одинаковых 0.656 секунды. Это подтверждает небольшую экономию
памяти контейнера без изменения конкурентности в этом эксперименте.

## Если заменить список генератором

```python
await asyncio.gather(*(fetch(client, url) for url in URLS))
```

Здесь нет исходного списка, но звёздочка всё равно полностью потребляет
генератор до вызова `gather`. Все корутины передаются в один вызов.
Это тоже не потоковая обработка URL и не ограничение числа задач.

## Как ограничить нагрузку

Число задач и число сетевых соединений — разные вещи. У HTTPX есть
лимиты пула соединений, но ожидающие соединения задачи всё равно занимают память.

`asyncio.Semaphore(50)` вокруг `fetch` ограничивает одновременное исполнение
защищённого участка. Если создать миллион задач через один `gather`, семафор
не отменит создание этих миллиона задач.

Простой способ ограничить число задач — обрабатывать URL порциями:

```python
async with httpx.AsyncClient(follow_redirects=True) as client:
    for start in range(0, len(URLS), 50):
        batch = URLS[start : start + 50]
        await asyncio.gather(*(fetch(client, url) for url in batch))
```

Здесь не больше 50 запросных задач в одной порции, но следующая порция ждёт
самый медленный запрос предыдущей. Для непрерывной обработки большого потока
подходит ограниченная `asyncio.Queue` и фиксированное число worker-корутин.
Результаты тоже нужно потреблять постепенно, если нельзя хранить их все в RAM.

## Ответ для защиты

«Обе записи передают в gather одинаковое число корутин и выполняют запросы
конкурентно. Во втором варианте временный список ссылок может освободиться
раньше, поэтому на больших объёмах возможна экономия памяти. Но обе версии
сразу создают задачи для всех URL. Для ограничения нагрузки нужны порции
или очередь с фиксированным числом обработчиков».
