# Как понять и защитить работу про асинхронность

Работа показывает, как Python может обслуживать несколько сетевых запросов,
пока каждый из них ждёт ответ. Основной вывод: `async def` разрешает писать
корутину, а способ запуска определяет, будут ли запросы ждать по очереди
или смогут перекрывать ожидание друг друга.

Начни с `task_0_fix_async.py`. Когда поймёшь разницу `slow_main` и `fast_main`,
переходи к сравнению с requests, ошибкам и вычислениям. Вопрос о двух вариантах
записи `gather` разобран отдельно в `answers.md`.

## Что мы скачиваем

В `common.py` заданы 20 адресов сервиса картинок. Они отличаются параметром
`seed`: например, `https://picsum.photos/seed/0/800/600`. Запрос сначала может
получить редирект, то есть указание перейти на другой адрес. Поэтому
`httpx.AsyncClient` создан с `follow_redirects=True`.

`response = await client.get(url)` получает ответ вместе с телом картинки.
В этих примерах мы скачиваем байты в память, но не сохраняем изображения
в отдельные файлы. Для заданий 0–2 достаточно HTTP-статуса, для задания 3
используем `response.content`, то есть скачанные байты.

`response.raise_for_status()` превращает неуспешный HTTP-статус в исключение.
Поэтому ответ с ошибкой сервера не будет незаметно принят за удачную загрузку.

## Словарь на примере кода

**Корутина** — выполнение функции, объявленной через `async def`, которым
можно управлять через `await`. Вызов такой функции возвращает объект корутины:

```python
coroutine = fetch(client, url)
```

В этот момент запрос ещё не отправлен. Чтобы корутина исполнялась, её нужно
ожидать или запланировать как задачу.

**Task** — задача, которую event loop может исполнять и возобновлять.
Её можно создать через `asyncio.create_task(coroutine)`.
`gather` умеет сам превратить переданные корутины в задачи.

**Event loop** — цикл событий, который управляет готовыми задачами и
ожиданиями. Когда одна задача ждёт сеть, он может продолжить другую.
В этих сетевых примерах код корутин исполняется в одном основном потоке.
Библиотеки и ОС могут использовать вспомогательные потоки, например для DNS.

**await** — дождаться результата awaitable. Если результат ещё не готов и
ожидание приостанавливается, управление может перейти event loop.
Само наличие слова `await` не гарантирует переключение: уже готовый результат
может быть получен сразу.

**Конкурентность** — несколько операций находятся в работе за перекрывающиеся
промежутки времени. **Параллелизм** — несколько вычислений физически
исполняются одновременно, например в разных процессах на разных ядрах.

## Задание 0 и ловушка с await

```python
for url in URLS:
    await fetch(client, url)
```

Представь три запроса длительностью по одной секунде. Сначала цикл ждёт
первый запрос, потом создаёт и ждёт второй, затем третий. Получается около
трёх секунд. Во время ожидания event loop свободен, но следующий запрос
этот цикл ещё не создал. Поэтому именно эти три запроса выполняются по очереди.

Исправление:

```python
coroutines = [fetch(client, url) for url in URLS]
statuses = await asyncio.gather(*coroutines)
```

Теперь все три корутины переданы планировщику. Пока первая ждёт сеть,
вторая и третья тоже могут отправить запросы и ждать ответы. В идеализированном
случае получится около секунды плюс накладные расходы. Реальный сервер,
канал связи и лимиты соединений могут сделать время больше.

Звёздочка нужна, потому что `gather` принимает отдельные аргументы:
`gather(coroutine_1, coroutine_2, coroutine_3)`. Список сам по себе не является
одной корутиной. Результат `gather` — список значений в порядке входных
аргументов, даже если запросы завершились в другом порядке.

Перенос списка внутрь `gather` сохраняет такую же конкурентность.
Подробность о времени жизни списка и эксперимент — в `answers.md`.

## Задание 1 и честное сравнение

В `sync_main` библиотека requests выполняет каждый запрос синхронно.
Следующая итерация начинается после получения предыдущего ответа.
`requests.Session` позволяет переиспользовать соединения.

В `fast_main` используется один общий асинхронный клиент для всех запросов.
Не нужно создавать отдельный AsyncClient на каждый URL: это мешает
переиспользовать соединения и добавляет накладные расходы.

Обе версии идут по редиректам, скачивают тела ответов и проверяют статус.
При этом один сетевой запуск не доказывает постоянный коэффициент ускорения:
сеть и сервер меняют задержки, а ранее запрошенные картинки могут кешироваться.
Чтобы сравнить две формы записи `gather`, отдельно используется эксперимент
без внешнего сервера.

В `timed` передаётся функция, запуск которой должен начаться после старта
таймера:

```python
timed("async", lambda: asyncio.run(fast_main()))
```

`lambda` создаёт маленькую функцию без аргументов. Если вызвать `asyncio.run`
до передачи в `timed`, запросы выполнятся ещё до начала замера.

## Задание 2 и падения запросов

Сеть может не отвечать, домен может отсутствовать, а сервер может вернуть
ошибку. Для каждого адреса `robust_fetch` выполняет до трёх попыток.

В каждой попытке есть `asyncio.timeout(3.0)`: оно ограничивает всё ожидание
одного запроса, включая редиректы. У HTTPX дополнительно установлен свой
таймаут. Его таймауты относятся к отдельным этапам сети и ожиданиям данных;
это не всегда то же самое, что общий лимит на весь запрос.

Если первая попытка неуспешна, ждём секунду. Если вторая тоже неуспешна,
ждём две секунды. После третьей ошибки выбрасываем исключение.
Три попытки — это первая попытка и два повтора. Для последовательности
пауз 1, 2, 4 секунды понадобились бы четыре попытки.

Пауза делается через `await asyncio.sleep(delay)`. Вызов `time.sleep(delay)`
внутри корутины занял бы поток event loop и мешал остальным запросам.

Повторяем сетевые ошибки, таймауты, HTTP 429 и ошибки сервера 5xx.
HTTP 404 означает, что адрес ресурса не найден: немедленно повторять тот же
запрос обычно не имеет смысла, поэтому он возвращается как ошибка сразу.
Это учебная политика повторов; для полноценного клиента можно учитывать
`Retry-After`, добавлять случайный разброс пауз и выбирать политику по API.

```python
items = await asyncio.gather(*coroutines, return_exceptions=True)
```

Флаг позволяет дождаться всех запросов. В списке оказываются либо статусы,
либо объекты исключений. Затем `robust_main` делит их на успешные результаты
и ошибки. В обоих списках есть исходный URL, чтобы понимать, к какому
запросу относится запись.

У обычного `gather` без флага первая ошибка передаётся ожидающей корутине.
Сам `gather` не отменяет автоматически остальные задачи. Если после этого
закрыть клиент или завершить `asyncio.run`, их дальнейшее выполнение может
быть прервано уже из-за этого окружения. Поэтому нельзя говорить, что
«gather всегда сам отменяет остальные».

Внешнюю отмену не считаем обычной сетевой ошибкой. `CancelledError`
не перехватывается в `robust_fetch`, чтобы задачу можно было остановить.

## Задание 3 и тяжёлые вычисления

CPU-bound означает, что время уходит на вычисления процессора. I/O-bound
означает, что программа преимущественно ждёт ввод-вывод, например сеть.

Сначала `cpu_main` скачивает картинки. Затем на одинаковых байтах сравнивает
два способа вычислить хеши. Загрузка отделена от сравнения CPU-части, чтобы
разная скорость сервера не маскировала поведение event loop.

Функция `heavy` берёт до 64 КиБ каждой картинки, размножает фрагмент в 1000 раз
и несколько раз передаёт его SHA-256. Ограничение фрагмента удерживает
временный буфер примерно в пределах 64 МиБ на процесс. Повторы делают
блокировку заметной даже на быстром компьютере.

Когда `heavy` вызывается прямо из корутины, поток event loop занят до её
возврата. Наличие `async def` снаружи не делает обычный синхронный код
автоматически неблокирующим.

`ticker` должен печатать точку каждые 0.1 секунды. Кроме точек, он измеряет
промежутки между пробуждениями. Большая пауза показывает, что event loop
не смог вовремя продолжить корутину. Это показатель отзывчивости; он
отдельный от общего времени вычисления.

```python
loop = asyncio.get_running_loop()
with ProcessPoolExecutor(max_workers=2) as pool:
    future = loop.run_in_executor(pool, heavy, body)
    result = await future
```

Здесь `heavy` работает в отдельном процессе. Основной event loop ждёт Future
и может исполнять `ticker`. В полном примере несколько таких Future собраны
в `gather`, а число одновременно работающих процессов ограничено двумя.
Запуск процессов и передача данных тоже стоят времени, поэтому важен
результат измерения, а не обещание постоянного ускорения.

Точка входа защищена `if __name__ == "__main__":`. При запуске нового процесса
Python импортирует модуль. Без этой защиты на macOS и Windows можно повторно
запустить создание процессов при импорте.

Уточнение про GIL: в обычной сборке CPython он ограничивает одновременное
выполнение Python-байткода потоками. Однако `hashlib` освобождает GIL при
обработке достаточно большого блока. Поэтому утверждать, что поток вообще
не подходит для SHA-256, неверно. В задании реализован именно пул процессов.
Даже при освобождении GIL прямой вызов `hashlib` остаётся блокирующим для
того потока, в котором работает event loop.

## Как показать проект преподавателю

Открой в PyCharm файл `task_0_fix_async.py`. Покажи цикл с `await`, затем
объясни, почему `gather` позволяет перекрыть ожидания. Запусти файл или
покажи уже сохранённые реальные замеры в README.

В `task_1_sync_vs_async.py` покажи, что у requests обычный цикл, а у httpx
все корутины передаются в `gather`. Объясни, почему в обоих случаях один
общий клиент и почему включены редиректы.

В `task_2_robust_fetch.py` покажи лимит попыток, таймаут, вычисление паузы
и `return_exceptions=True`. В выводе найди успешные URL и ошибки по битым
адресам. Если внешний сервис с задержкой в этот раз вернулся быстро,
проверка настоящего таймаута есть в тесте с незавершающимся обработчиком.

В `task_3_cpu_bound.py` запусти сравнение и наблюдай точки. Покажи максимальную
паузу ticker и совпадение хешей. Главное здесь — event loop снова может
работать во время вычислений в других процессах.

Для вопроса о записи `gather` открой `gather_nuance.py` и `answers.md`.
В эксперименте число дочерних задач совпадает у всех трёх вариантов.
У варианта со списком в переменной остаётся дополнительный контейнер ссылок.

## Короткие ответы на вопросы

| Вопрос | Ответ |
| --- | --- |
| Почему async не ускорил цикл? | Следующий запрос создаётся после await предыдущего. |
| Что делает вызов async-функции? | Создаёт объект корутины; тело ещё не исполняется. |
| Кто создаёт Task в примере? | gather, получивший объекты корутин. |
| Где переключение? | При ожидании, которое действительно приостанавливает корутину. |
| Что делает `*`? | Распаковывает iterable в отдельные аргументы вызова. |
| Каков порядок результатов gather? | Порядок переданных аргументов. |
| Список внутри gather делает всё последовательным? | Нет, конкурентность сохраняется. |
| Генератор под `*` ограничит число задач? | Нет, его полностью распакуют до вызова. |
| Семафор уменьшит число созданных Task? | Нет, если заранее создать все задачи. |
| Зачем пул процессов? | Выполнять тяжёлую функцию вне потока event loop. |
| Почему процессы не всегда быстрее? | Есть расходы на запуск, передачу данных и координацию. |

Подробные первичные источники перечислены в README.md.
